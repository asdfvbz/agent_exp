# 设计取舍

README 讲"怎么用",这里讲"**为什么是这样**"。

绝大多数是踩过之后才改的 —— 每条都注明了代价。

---

## 为什么计数器不写进经验文件

经验文件要 commit,团队共享。而注入 / 复发是**高频写的机器遥测**。

写进被 commit 的文件意味着:每天几十次冲突,而且**冲突发生在
人类写的正文旁边** —— 解决冲突时手一抖就可能损坏内容。

所以切开:

| | 位置 | 进 git? |
|---|---|---|
| 经验正文 + 状态(`status`) | `.exp/lessons/*.md` | ✅ 是 |
| 计数(`injected` / `recurred` / `missed`) | `.exp/stats.json` | ❌ 否 |

副作用是计数是**本机的**,不是全队的。但这本来就该是本机信号 ——
"这条经验在我这儿有没有用"和"在你那儿有没有用"是两件事。

> 实现上还有个约束:`bump` **绝不重写经验文件**,只写 `stats.json`。
> 有测试守着这条(`test_counters_not_in_lesson_file`)。

## 为什么写盘前要回读校验

一个字符的错误(星号、英文引号进 YAML)会让**所有**读该文件的工具
同时报错 —— 排查时你看到的是四五个不相关的报错,指向完全不同的地方。

所以 `Layer.save()` 在写之前**先序列化、再解析回来、比对 id**。
对不上就不写,直接抛错。

**代价:** 每次写入多做一次解析。**收益:** 一个坏文件都进不去。

## 为什么主题是算出来的,不是存下来的

经验库里的字段分三种,存法不同:

| 类型 | 例子 | 存不存 | 为什么 |
|---|---|---|---|
| **状态** | `status`(confirmed / refuted) | ✅ | 状态机 —— 互斥、穷尽、**不需要"其他"桶** |
| **决定** | `layer`(global / project) | ✅ | 二分 —— 判据是"换任何仓库成立吗",答是或否 |
| **主题** | 分类 / 标签 | ❌ | 永远会出现新主题 → **永远需要"其他"桶** |

**判据一句话:这个归类需要「其他」这一类吗?需要 → 它一定会烂。**

存下来的主题必然腐烂:新经验放不进 → 塞进最接近的桶 → 那个桶变成垃圾桶
→ 没人记得边界在哪。

所以 `category` 只是个**可选的人工翻阅视图**(`exp list --by category`),
**不进检索打分堆** —— 它会稀释真正有效的 `trigger`。

替代方案是现算:

```bash
exp cluster          # 按触发词相似度聚类
exp show <id>        # 末尾的"相关"是算出来的
```

### 聚类为什么也不落盘

聚类**不稳定** —— 加一条经验,整个分组会移位;换个特征,分组又变了。

> **用弱信号(措辞)做永久性结构决定,比不做决定更危险。**

检索是软的:匹配错了只是这次没显示。聚类是硬的:分错了组,
你可能据此合并两条无关的经验、删掉一条其实有用的。

所以它每次现算,结果只在屏幕上。

### 容量问题的真正危害不是"没列出来"

修容量问题时想清楚了一件事:**被截断的经验依然能被 `exp query` 检索到。**
它们只是不常驻,不是不可达。

所以危害不在"少了 10 条",而在于:

> **模型不知道库比它看到的列表大。**

上一版的截断提示写的是"**索引已满,跑 `exp cluster` 看哪些该合并**"——
那是给**维护者**看的。而读这段文字的是**模型**,它既不会跑 `cluster`,
也不会去合并经验,只会把这句当噪声跳过。

改成告诉它"库里共 N 条,没列出的用 `exp query` 一样能查到",成本一行字,
效果是把**静默失效**变成**已知的不完整**。这两者的差别是巨大的:
前者库里显示"一切正常",后者模型知道自己该去查。

顺带修正了一个更基础的错配:真正约束成本的一直是**字符预算**,
而 `INDEX_MAX_ITEMS` 那个条数上限把一半预算浪费了
(40 条 × 49 字符 ≈ 2000 字符,而预算是 4000)。
现在条数只作防爆上限,有效容量由字符预算决定 —— 实测覆盖从 40 条提到 100 条,
**不增加一分上下文开销**。

### 排序键的稳定性也是正确性

索引排序的最后一级原来是 `l.title`。同档条目按字符串排,于是
`经验46` < `经验5` < `经验6` —— 跟新旧、重要性都无关。

后果不是"不好看",而是**在中间插一条新经验会让整个被挤掉的集合重新洗牌**。
而被挤掉这件事决定 `starved_index` 认定谁"从没露过面",也就决定
`gc` 报谁。用一个任意的顺序去决定一个会被报出来的诊断,是不可接受的。

改用 `created` 做末级排序:新经验不会无故把老经验挤出去,截断结果可预测。
中间一级也从 `-recurred` 换成了 `injected > 0` —— 依据是这个项目自己的
那句话:**库的价值不是条数,是被命中过多少条**。一条从没被查过的经验
占着格子挤掉一条天天用的,是净损失。

### 那什么时候才真需要分层

可测量的信号,不是理念:

```python
INDEX_MAX_ITEMS = 40      # 索引容量
```

索引装不下时,**被漏掉的经验永远不会被注入** → 它们的 `missed`
永远算不出来 → 库里显示"一切正常",而实际有一批经验从没机会出现。

**这是最隐蔽的失效模式。** 所以 `render_index` 截断时会**明确报告**,
而且这段警告会进入模型的上下文。

> 注意区分两件事:**检索容量**要到 40 条以上才是问题;
> 而**整理**(找重复、找可合并的)在任何规模下都有价值。
> `exp cluster` 两者都报。

## 为什么归因要分「怎么匹配上的」

归因要判两件事:这条经验**该不该**在这次失败里出现,以及它**有没有**出现。
后者靠 `injections.jsonl` 记账,前者靠检索 —— 而检索有两档精度:

| | 依据 | 性质 | 会假阳性? |
|---|---|---|---|
| **骨架** | 挂了签名,失败签名精确命中 | 结构性断言 | 不会 |
| **语义** | 失败信息做二元组比对 | 启发式 | 会 |

上一版把两者一视同仁:只要"没送到"就记 `missed`。看着合理,实际是错的 ——

签名命中是**硬证据**:系统确知这是同一种失败。它身上出的岔子只可能出在投递端。
把它记成"检索漏检",等于告诉用户"你的触发词写偏了",而那条触发词
从来就没被查过 —— 失败是靠签名对上的。用户会去改一个没问题的字段。

所以拆开了:

|  | 看过做法 | 没送到 |
|---|---|---|
| 骨架命中 | `recurred` → 改 fix | **`starved` → 改投递** |
| 语义命中 | `recurred` → 改 fix | `missed` → 改 trigger |

**结构性信号不产生 `missed`,启发式信号才产生。** 跟 `min_overlap` 卡在 4
是同一条原则:**归因写错比不写更坏。**

---

## 为什么 `starved` 不是又一个负信号

库里原本全是负信号(`recurred` / `missed` / `dead`),外加一个要手工标的
`helped`。`starved` 是第一个**机器算出来的正面相关性证据**:

> 这条经验反复撞上真实失败,却从没被送到模型眼前。

它的结论不是"这条经验不好",而是"**这条经验有用,是我的投递策略在拖后腿**"。
所以它不该驱动"改 trigger",该驱动两件事:

1. `exp gc` 把它单列一类,并明说**别动 trigger**
2. **索引排序里提到前面**

第 2 条是在打破一个自我锁定的死循环:被容量挤掉的经验 `indexed` 恒为 0,
而原排序把它们压在最后 —— 越饿死越靠后,越靠后越饿死。
一条被证明反复撞上的经验,比一条刚写完还没人踩过的更该占那 40 个格子之一。

---

## 为什么"进过索引"要单独记

`is_dead_weight` 原来的判据是"创建 ≥30 天且注入 0 次"。这是错的 ——
**两种完全不同的东西在数据上长得一模一样:**

| 现象 | 病因 | 处方 |
|---|---|---|
| 进过索引,没人拉全文 | 经验本身没价值 / trigger 不吸引人 | 删掉,或重写 |
| **从没进过索引** | 索引装不下,它排在 40 名开外 | 扩容量,**不许删** |

上一版全判成死重。50 条经验、上限 40 条时,实测有 10 条 `injected` 永远会是 0 ——
30 天后它们会集体被报成"死重 / 触发词写偏了",而真相是容量。

这跟 `missed` 的失效模式**是同一个**,只是发生在容量层:

> 信号算不出来 ≠ 一切正常。被挤掉的经验 `missed` 也永远是 0,
> 库里显示"一切正常"。

`exp gc` 早就为 `missed` 写过这条警告(见上面「为什么主题是算出来的」一节),
却让 `dead` 原样踩了进去。

### 判据必须是事实,不能是推断

第一版修的时候,`is_starved_index` 的判据是"创建 ≥30 天 + `indexed` == 0"。
**这还是错的** —— 它把"从没被渲染过"和"渲染过但没挤进去"混为一谈了,
只能靠年龄去猜,于是信号要 30 天后才出现。

正确的做法是**在索引渲染的那一刻记账**:谁没挤进去,当场 `excluded += 1`。
这样判据变成 `excluded > 0 and indexed == 0`,是**已经发生的事实**:

- 一条今天刚写、今天排在 41 位的经验,**今天**就被报出来
- 不用等,也不用猜

> **死重**需要时间(这条经验可能只是还没被用上,不是没用);
> **容量溢出**不需要 —— 50 条经验、上限 40 条,是算术。
> 把需要等待的判据套在不需要等待的问题上,只会推迟信号。

这和整个项目的核心教训是同一条:**能让机器确定的事,别让它去推断。**

## 为什么计数器和会话身份绑得这么死

**这一节是修一个真实 bug 之后补的。**

`recurred` 的判据是"注入过之后还犯",而"注入过"要跨进程查 ——
注入发生在 `SessionStart` 进程,归因发生在 `PostToolUseFailure` 进程。
两者靠 `session_id` 对上号。

上一版的 `session_id()` 长这样:

```python
os.environ.get("CLAUDE_SESSION_ID") or f"pid{os.getppid()}"
```

环境变量没设时,回退到父进程 pid。**而 hook 命令是
`python3 x.py || python x.py`,中间隔着一层 shell** —— 实测在 git-bash 下
每次调用都新起一个中间 shell,于是 `ppid` 每次都不同:

```
第 1 次失败  → 注入记在 pid9024 名下
第 2 次失败  → 去 pid10516 名下找 → 找不到 → 记 missed
```

后果是 `recurred` **恒为 0**,所有签名精确命中的复发都被记成
"触发词写偏了"。而症状是**静默的** —— 界面一切正常,只是永远
不会有经验被标记为坏的。

修法有两条,缺一不可:

1. **用 payload 里的 `session_id`** —— Claude Code 每个 hook 事件都带它,
   这是权威且必然存在的来源。环境变量只用于手工跑 CLI 的场景。
2. **拿不到就返回空,不要编。** 归因拿不到身份时显式跳过 recurrence 判定
   (骨架命中仍记 `starved`,那不需要身份)。宁可少一个信号,
   也不拿错的 id 污染计数。

> **这个 bug 是被测试结构藏住的。** 旧测试在 `TestAttribution` 里
> 手抄了一份归因逻辑(`_fail()`),测的是抄本而非实现;而且调
> `log_injection(..., exp.session_id())` 时,开发机上碰巧有
> `CLAUDE_SESSION_ID`,等于替真实环境把变量补上了。
> 现在归因用例一律从 stdin 进、从计数器出 —— 见 `Base.hook()`。
>
> 讽刺的是,这**正是本项目诞生时踩过的那个坑**(见下节:CI 以为覆盖了
> 两条路径,其实测的是同一条)。教训不是"要写测试",而是
> **测试必须打真实入口**。

## 为什么零依赖

经验库在**会话启动路径**上。它挂掉会拖垮整个会话。

所以:纯标准库。装了 PyYAML 就用,没装就走内置的极简 YAML 子集
(只支持我们自己写出去的那几种模式)。

**代价:** 得自己维护一个 YAML 子集实现,而且它出过 bug ——
转义还原漏了,`有"引号"` 读回来变成 `有\"引号\"`。

**这个 bug 教会我们一件事**(见下)。

### "我的环境里没事"是最不该被容忍的缺陷

那个转义 bug **只在没装 PyYAML 的机器上出现**。

当时的 CI 是「不装 PyYAML 跑一遍 / 装了再跑一遍」—— 听起来覆盖了两条路径。
**但很多 runner 自带 PyYAML**,所以"不装"那条实际也在用 PyYAML。
两条路径测的是同一个东西。

而测试本身只断言了"能解析",**没断言值相等**,所以值被改坏也照样绿。

两头都修了:

- CI 改用 [`tests/run_without_pyyaml.py`](../tests/run_without_pyyaml.py) ——
  **真的劫持 `__import__` 屏蔽 yaml**,并自检"屏蔽是否生效"
- 新增测试断言**值原样回来**,不只"能解析"

## 为什么经验文件带 schema 版本号

经验是**用户的数据资产**。

插件升级时如果 frontmatter 格式变了,没有版本号就只能靠猜 ——
而猜错 = 弄坏用户数据。**这是开源项目最不可原谅的错误。**

所以每个文件带 `schema:` 字段(缺失视为 0),`exp migrate` 按版本升级,
**默认 dry-run**,`--apply` 才写。

现在只做"补版本号"这一件事;将来格式再变时,在那里加按版本的转换分支。

## 为什么有解析缓存

`post-failure` 挂在**每次工具失败**上 —— 一轮密集调试能触发几十次。

| | 199 条经验耗时 |
|---|---|
| 无缓存 | ~280 ms |
| 磁盘缓存 | **~88 ms** |

按 `(mtime, size)` 失效,所以手改文件、`git pull` 都会自动重算。
另有进程级缓存在 `exp serve` 场景下把重复调用降到 ~7ms。

**坑:** 计数变更后必须清进程缓存 —— 经验文件没变(文件签名没变),
但计数变了。不清的话同进程内读到的还是旧计数。

## 为什么需要跨进程锁

两个会话同时跑时,"读 → 改 → 原子替换"会让后写的覆盖先写的,
**计数静默丢失**。

而计数是这个系统**唯一的信号来源** —— "少记几次"和"没记"在诊断上
是同一件事:你都查不出哪条经验是坏的。

实现上踩了两个 Windows 特有的坑:

1. **删被占用的文件抛的是 `PermissionError`,不是 `FileExistsError`。**
   上一版把它归进"建不了锁"直接放行,于是那些进程**无锁写入** ——
   实测 40 并发丢 10 次。现在任何获取失败都重试。
2. **拿着 fd 去 unlink 在 Windows 上必然失败。** 所以创建后立刻 `close(fd)`。
   否则锁永远删不掉 —— 而加锁的死锁比不加锁的丢数据更糟。

**设计决定:宁可等待,不可静默丢弃。** 临界区只有几毫秒,
等待的代价远小于丢信号。超时给到 120s,让"拿不到锁"变成真正的异常情况
而不是常态路径。

实测 40 并发 → 40/40,**0.4 秒**。

## 为什么用 `PostToolUseFailure` 而不是 `PostToolUse`

`PostToolUse` 文档明确说是"工具调用**成功**后"触发。
捕获失败必须用 `PostToolUseFailure`,它带 `error` / `error_type` / `is_timeout`。

另外:该事件**无法阻断任何东西**(工具已经失败了),但它支持
「exit 2 → stderr 送给 Claude」—— 我们用它把"这个坑记过"的提示
送到模型眼前。走 stdout 是送不到的。

## 为什么定位是编程

内核是**领域无关**的 —— 它不知道什么是"编程",只知道三件事:

| 概念 | 编程域里是什么 |
|---|---|
| **捕获源** —— 什么算一次失败 | 工具报错 / 测试失败 / 编译错误 |
| **校验源** —— 怎么知道有没有再犯 | 跑测试 |
| **经验本体** | trigger / 根因 / 做法 / 归因计数 |

非编程域理论上能接,代价是实现这两个适配器 ——
**而且大概率接不动**,因为别的领域失败不报错、也没法自动验证。

这不是设计缺陷,是"经验库只在反馈客观的地方有用"的直接后果。

所以:**引擎保持通用,承诺只给编程域。**

---

## 为什么不用向量库

不用 embedding 检索,理由是具体的:

- **零依赖是硬约束。** 经验库在会话启动路径上,它挂掉会拖垮整个会话。
  一个会因为网络问题报错的校验器是不可信的。
- **中文二元组对自定义术语够用。** 「追读率」「风格锁」这类词在通用词典里
  未必存在,分词需要词典而二元组不需要。
- **成本随库大小线性增长。** 100 条约 9k token,300 条约 27k。
- **分层比向量化更值得做。** 索引常驻(标题 + 触发词)、正文按需加载,
  能把成本从线性压成对数 —— 这就是 `INDEX_MAX_ITEMS` 那套。

**已知代价:** 匹配不到同义表达。经验写"阈值",你查"标准值",不会命中。
所以 `trigger` 措辞要贴近你实际会想到的词 —— `missed` 计数就是用来
暴露这个问题的。

> 如果将来要加语义检索,它应该是**可选层**:显式开启,
> 失败时静默退回字面结果,不能成为可用性的单点。

---

## 这个机制是从哪来的

最早在一个 AI 写小说的项目里孵化。

那批"写作经验"里活得最久的几条 —— **YAML 静默失败、阈值必须有来源、
度量工具要覆盖输入形态、散列要基于语义** —— 其实全是**编程经验
穿了个写作的马甲**。

**经验的价值向"反馈客观"的地方聚集。** 工程类的坑自己会喊(退出码、
测试失败),写作类的坑不喊。所以后者要么记不下来,要么记下来也是
含糊的 —— 而含糊的 `fix` 注入了也没用。

这件事本身就说明了为什么定位是编程。
