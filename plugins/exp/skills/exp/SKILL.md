# exp — 两层经验库

**存在的理由:同一个错误犯第二次是浪费。**

这个工具解决的是一个很具体的问题:经验记下来了,但**做事之前想不起来**。
所以它的每条经验都有一个「触发词」字段,措辞是「当你正在做 X 时」——
检索靠它。

## 两层

| 层 | 位置 | 特点 |
|---|---|---|
| **项目级** | `<项目>/.exp/` | 跟着 repo 走,可 commit,团队共享。**更当用。** |
| **全局级** | `~/.exp/` | 跟着人走,跨项目复利。检索时降权,但跨项目的坑靠它。 |

检索时两层自动合并,不需要你选。

## 什么时候必须查

**动手之前**,尤其是这些场景:

- 要改构建/配置文件、写 YAML、动 schema
- 要设一个数值阈值(字数、占比、超时、重试次数)
- 要写一段"上次也是这么写的"代码
- 遇到一个报错,而你觉得自己见过它
- 开始一个多步骤的重构或迁移

```bash
exp query "<你正要做什么>"
```

用**你实际会想到的词**去查,不要用抽象描述。
查「我要设一个字数下限」比查「关于阈值的考量」命中率高得多。

## 什么时候必须记

**踩到坑的那一瞬间**,如果它满足**两条**:

1. 这个坑**会再踩**(不是一次性的配置调整)
2. 它**没有天然的归属地**(不在代码注释里、不在 README 里)

记的时候,**触发词是最重要的字段**。没有触发词等于没记——
检索不到它。写「当你正在写对话为主的章节时」,不要写「关于对话章的思考」。

```bash
exp add "标题" --category 基架 \
    --trigger "当你正在做 X 时" \
    --root-cause "为什么会这样" \
    --fix "具体怎么做" \
    --severity high
```

`--fix` 必须**可执行**。「注意同步一下」不是 fix,「改完 schema 立刻跑 `make gen`」
才是。**fix 不可执行的经验,注入了也没用——这正是 `gc` 要抓的东西。**

### 能给经验挂签名就挂

`--signature` 是可选的,但挂了体验完全不同 —— 系统会在**每次工具失败**时
拿它精确匹配,失败时直接把做法送到你眼前(不用你主动查),而且能自动判
「看过还是犯」。没挂签名也能靠措辞模糊匹配,精度低一截。

签名从哪来:`exp distill` 会列出真实失败事件的签名,照抄即可。

```bash
exp distill              # 看有哪些反复出现的失败,附签名
exp distill --write      # 生成草稿文件,含签名和填空模板
```

## 机器在自动做什么

启用了插件的项目里,有三件事**不依赖你的自觉**:

| 时机 | 动作 |
|---|---|
| 会话开始 | 注入经验索引(标题 + 触发词) |
| 工具失败 | 算签名 → **把做法直接送到你眼前** → 归因 |
| 回合结束 | 把重复失败归拢成候选,供 `exp distill` 归纳 |

**归因是自动的,不需要人标注。** 它按「怎么匹配上的 × 有没有送到你手上」
分出四种毛病,四种处方各不相同:

- **`recurred`(反复复发)** —— 看过做法还是犯。说明 **fix** 不可执行。
- **`missed`(检索漏检)** —— 该命中没命中。说明 **trigger** 写偏了。
- **`starved`(投递饿死)** —— 签名精确命中却从没送到。**不是经验的问题**,
  别去改 trigger,改了也没用。
- **`starved_index`(索引饿死)** —— 索引装不下,它从没露过面。
  该扩容量,别删经验。

只有前两种该去动经验本身。连续复发到阈值,经验会被自动标记 `needs_rewrite`。

## 常用命令

```bash
exp query "<我要做什么>"        # 检索(最常用)
exp show <id>                   # 看全文
exp list                        # 全部,按层级/分类聚合
exp list --health rotten        # 只看反复复发的
exp add "<标题>" --trigger "..." --fix "..."
exp feedback <id> --outcome helped|recurred|confirmed|refuted
exp distill                     # 把原始事件归纳成候选经验
exp gc                          # 体检:反复复发 / 检索漏检 / 死重
exp serve                       # 开网页看(带健康度面板)
```

## 什么时候该动 `gc`

**别让它变成仪式。** 看这两个信号就够了:

- `exp gc` 报出**反复复发** → 这条经验的 fix 是废的,重写它,别再加新经验
- `exp gc` 报出**死重**(进过索引却没人拉全文) → 触发词不吸引人,或它本就不该记
- `exp gc` 报出**饿死**(投递/索引) → **别动经验**。这是投递策略或容量的问题,
  改 trigger 或删经验只会把有用的东西弄坏

**库的价值不是条数,是被命中过多少条。** 一个 200 条、190 条从没被检索过的库,
不如 20 条全部在用的库。

## 边界

- **`exp` 不调 LLM。** 捕获、归因、聚类全是机器算的。归纳交给你——
  你有当前会话的完整语境,比任何外部调用都更懂当时发生了什么。
- **原始事件在 `<项目>/.exp/raw/`,不进 git**(噪声)。
  经验本身在 `lessons/`,**要 commit** —— 跨机器、跨协作者共享才是它的价值。
- **写盘前会回读校验。** 解析不出来的内容不会被写入——
  这条是踩过坑的:一个虚构字符能让所有读该文件的工具同时报错。
